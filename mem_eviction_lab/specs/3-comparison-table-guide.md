# Comparison Dashboard — Collapsible Column & Metric Guide Spec

This document specifies the design and implementation plan for adding a collapsible metric explanation guide and column-header hover tooltips to the multi-run **Memory Limit Sweep Comparison** section of `dashboard.html` generated by `cmd/visualizer`.

## 1. Goal & Scope

The comparison table (`#comparison-table`) at the top of multi-run dashboards condenses ten metrics spanning userspace `/proc/<pid>/pagemap` scanning and Linux kernel cgroup v2 (`memory.stat`, `memory.events`, `memory.pressure`) accounting. Adding a built-in, collapsible reference directly above the table makes the standalone HTML artifact self-explanatory for both talk audiences and readers inspecting archived sweeps, without cluttering the default view for repeat users.

**Scope**:
- Applies to the multi-run `#multi-run-section` (`PAYLOAD.multi_run === true`). Single-run dashboards hide `#multi-run-section` and remain unchanged.
- No changes to `cmd/manager`, CSV/JSON schemas, or `DashboardPayload` serialization are required; this feature lives strictly inside [`internal/visualizer/template.go`](../internal/visualizer/template.go) and its tests in [`internal/visualizer/visualizer_test.go`](../internal/visualizer/visualizer_test.go).

## 2. Placement, Layout & Interaction Design

### 2.1 Collapsible Guide Panel (`<details id="comparison-guide">`)
- **Placement**: Rendered inside `#multi-run-section` directly below `<h2>Memory Limit Sweep Comparison</h2>` and immediately above the `#comparison-table` `.card.table-wrap` container.
- **Default state**: Collapsed (`<details>` without `open`).
- **Summary bar (`<summary>`)**:
  - Styled as an interactive card header matching `--card` / `--card-hover` / `--border` theme tokens, with a custom rotating chevron indicator, title **"How to Read This Table — Metric & Kernel Source Guide"**, and subtle right-aligned hint (`"Click to expand"` / `"Click to collapse"`).
- **Expanded body structure**:
  1. **Page Lifecycle Primer**: A compact horizontal 4-step visual callout strip at the top explaining how an executable binary page moves through RAM under cgroup pressure:
     - **1. Cold Fault (`0 → 1`)**: First-ever access loads a 4 KiB page of `.text`/`.rodata`/`.data` from disk into page cache.
     - **2. Clean Eviction (`1 → 0`, stays `0`)**: Cgroup limit forces kernel reclaim to drop unused startup/`init()` pages; never needed again (**free memory savings**).
     - **3. Binary Refault (`1 → 0 → 1`)**: Reclaimed page was actually still active; CPU touches it again and stalls waiting to fault it back from disk.
     - **4. Page Thrashing / OOM Kill**: Non-reclaimable `anon` + `kernel` squeezes file cache below the active binary working set, causing continuous refaults, high PSI `full` stalls, or cgroup `oom_kill`.
  2. **Grouped Column Cards (4 Logical Groups, Left-to-Right Order 1–10)**:
     Each group has a compact section header and a responsive CSS grid (`grid-template-columns: repeat(auto-fit, minmax(300px, 1fr))`) of column definition cards. Every column card displays:
     - Column number pill (`#1`..`#10`) + exact column header title
     - Monospace **Source** tag (exact `procfs` / `cgroupfs` file & field)
     - **Plain-English meaning**
     - **Interpretation & caveats** (what good vs. bad looks like, edge cases, and sampling nuances)

### 2.2 Column Header Hover Tooltips (`<th>` in `#comparison-table`)
- Every `<th>` in `#comparison-table` carries a `data-tip="..."` attribute with a concise 1–2 sentence at-a-glance summary and source, plus `tabindex="0"` and a subtle dotted underline affordance (`text-decoration: underline dotted`) so viewers know headers are hoverable and keyboard-focusable.
- **Viewport-safe floating tooltip (`#th-tooltip`)**: Because `.table-wrap` uses `overflow-x: auto` (which per CSS Overflow clips any `position: absolute` child extending above/outside the scroll box), hover/focus renders into a single `position: fixed` `#th-tooltip` element attached to `<body>` styled consistently with the dashboard's ECharts dark tooltips (`rgba(15, 23, 42, 0.96)`, `#334155` border, max-width `320px`), clamping `left`/`top` inside `window.innerWidth` so edge columns (`Run`, `Samples (Reclaim)`) never clip off-screen.

## 3. Exact Column Content Specification (Columns 1–10)

Columns are grouped into four subsystems while preserving strict left-to-right table order:

### Group A: Run Setup & Verdict (Columns 1–3)

1. **`Run`**
   - **Source**: Run config `name` + result directory basename (`run_meta.json`).
   - **Meaning**: Experiment identifier and output directory for each sweep point.
   - **How to read**: Multi-run sweeps are automatically sorted from unconstrained (`Unlimited (max)`) down to the tightest `memory.max`. Click any row to load that run into the **Run Deep Dive** charts below.
2. **`Memory Limit`**
   - **Source**: cgroup v2 `memory.max` + `memory.swap.max` (`CLONE_INTO_CGROUP` at `t=0`).
   - **Meaning**: Hard memory ceiling enforced on the Collector leaf cgroup before `execve` begins (`Unlimited (max)` for the unconstrained baseline).
   - **How to read**: With `memory.swap.max=0` (default), anonymous Go heap/stack pages cannot be swapped out, so every byte above `memory.max` must be reclaimed by evicting clean file-backed pages (primarily the Collector binary).
3. **`Outcome`**
   - **Source**: Manager `classifyVerdict()` over `memory.events:oom_kill`, exit status, `pagemap` refaults, and `memory.pressure`.
   - **Meaning**: Automated classification of how the Collector tolerated this `memory.max` ceiling, evaluated in priority order:
     - `oom_killed`: Cgroup OOM killer terminated the Collector (`memory.events:oom_kill > 0`) because non-reclaimable `anon + kernel` memory left no evictable file pages to satisfy a fault.
     - `process_error`: Collector failed startup readiness within `startup_timeout` or exited early non-zero without an OOM kill. *(Tip: check `Binary Refaults` and `PSI Full Stall`—severe startup thrashing during Go `init()` can time out readiness before `oom_kill` fires.)*
     - `no_reclaim`: Zero binary evictions and `memory.events:max == 0`; memory stayed comfortably below the limit.
     - `thrashing`: Active binary pages repeatedly faulted back in or stalled execution: `(thrashing_pages > 0 && (total_refaults >= 64 || total_refaults / ever_faulted_pages >= 5%))` **or** `PSI full stall >= 100 ms` (where `thrashing_pages` = pages refaulted $\ge 2\times$).
     - `clean_reclaim`: Kernel reclaimed unused binary pages while keeping refaults and PSI `full` stalls below the thrashing thresholds.

### Group B: Collector Binary Tracking — Userspace `pagemap` (Columns 4–6)

4. **`Peak → Final Binary`**
   - **Source**: `/proc/<pid>/maps` (binary `dev:ino` VMAs) + `/proc/<pid>/pagemap` (`PM_PRESENT`, bit 63).
   - **Meaning**: Highest sampled resident Collector ELF footprint (`Peak`) vs. resident binary footprint on the last live sample (`Final`), including clean file pages (`.text`, `.rodata`) and private CoW `.data` pages.
   - **How to read**: Comparing `Peak` (or the `max` baseline) against `Final` shows how aggressively the kernel compressed the resident binary footprint to make room for the Go heap.
5. **`Cleanly Evicted`**
   - **Source**: `/proc/<pid>/pagemap` per-page state machine (`cleanly_evicted_pages × page_size`, `% of ever_faulted_pages`).
   - **Meaning**: Binary memory that was faulted into RAM at least once (e.g., unused component `init()` functions and registration tables), evicted by reclaim, and **never faulted back in** (`0` refaults) for the rest of the run.
   - **How to read**: Higher (with low refaults) is pure win—dead binary weight shed from RSS at zero ongoing CPU or I/O cost.
6. **`Binary Refaults (0→1 / PFN)`**
   - **Source**: `/proc/<pid>/pagemap` bits `63` (`PM_PRESENT`), `61` (`PM_FILE`), and `0..54` (`PFN`).
   - **Meaning**: Cumulative sampled count of times an evicted 4 KiB Collector binary page had to be faulted back into RAM because execution touched it again (`total = 0→1 + PFN`):
     - **`0→1`**: Poll caught the page evicted (`0`), then a later poll saw it resident (`1`) again.
     - **`PFN`**: Clean file page stayed resident (`1`) across consecutive polls, but its physical Page Frame Number changed—catching fast evict + re-allocate cycles inside a single `50–500 ms` poll gap.
   - **Caveats**: Lower bound during extreme thrashing (multiple refaults of the same page inside one `50 ms` window count once). Conversely, minor `PFN` shifts can occasionally occur on unconstrained runs due to kernel page compaction/migration without memory pressure (verify via `Major Faults == 0` and `PSI Full Stall == 0 ms`).

### Group C: Kernel Reclaim & Pressure — `cgroup v2` (Columns 7–9)

7. **`Kernel Refaults`**
   - **Source**: cgroup v2 `memory.stat` → `workingset_refault_file`.
   - **Meaning**: Exact kernel shadow-entry counter (`mm/workingset.c`) of evicted file-backed pages in this cgroup that were re-faulted soon enough (within active/inactive LRU distance) to signal working-set thrashing.
   - **How to read**: Unlike sampled `Binary Refaults`, this never misses rapid sub-poll refault bursts, so it is often higher under heavy thrashing; however, it counts all file pages in the cgroup and cannot attribute refaults to specific ELF sections.
8. **`Major Faults`**
   - **Source**: cgroup v2 `memory.stat` → `pgmajfault`.
   - **Meaning**: Total major page faults in the cgroup where a missing page required synchronous filesystem/disk I/O (`VM_FAULT_MAJOR`).
   - **How to read**: Note that sequential faults benefit from kernel mmap readahead (one major fault can prefetch up to 16 adjacent pages that subsequently resolve as minor faults), whereas random-access thrashing drives `pgmajfault` sharply upward.
9. **`PSI Full Stall`**
   - **Source**: cgroup v2 `memory.pressure` → `full total=` (converted from $\mu\text{s}$ to $\text{ms}$).
   - **Meaning**: Cumulative wall-clock milliseconds during which **all** non-idle threads in the Collector cgroup were simultaneously stalled waiting on memory reclaim or disk refault I/O.
   - **How to read**: The ultimate measure of user-visible pain. Near `0 ms` means reclaim was invisible to Collector throughput/latency; hundreds or thousands of ms means execution stalled severely on the thrashing cliff.

### Group D: Telemetry Sampling (Column 10)

10. **`Samples (Reclaim)`**
    - **Source**: Manager hybrid sampling loop (`epoll` `EPOLLPRI` on `memory.events` with `50 ms` debounce + `500 ms` periodic ticker).
    - **Meaning**: Total `/proc/<pid>/pagemap` + cgroup snapshots recorded (`Samples`), and in parentheses how many were triggered specifically by cgroup reclaim activity (`reclaim_event` + `reclaim_debounced`) rather than the `500 ms` heartbeat.
    - **How to read**: `(0)` reclaim samples confirms `memory.max` was never hit; a high reclaim-sample count shows continuous `memory.events:max` direct-reclaim wakeups.

## 4. Implementation & Verification Plan

1. **Update [`internal/visualizer/template.go`](../internal/visualizer/template.go)**:
   - Add CSS styles for `.guide-details`, `.guide-summary`, `.lifecycle-strip` / `.lifecycle-step`, `.guide-group`, `.guide-grid`, `.guide-item`, `.source-tag`, `th[data-tip]`, and floating `#th-tooltip`.
   - Insert `<details id="comparison-guide" class="card guide-details">` inside `#multi-run-section` directly above `#comparison-table`'s `.card.table-wrap`, containing the Page Lifecycle primer and the 4 grouped column sections (10 cards total, including all 5 `Outcome` badges rendered with `.badge-*` styles).
   - Annotate all 10 `<th>` headers in `#comparison-table` with concise `data-tip="..."` attributes and `tabindex="0"`, add `<div id="th-tooltip" role="tooltip"></div>`, and wire hover/focus/scroll/escape handlers in dashboard JS with viewport boundary clamping.
2. **Update [`internal/visualizer/visualizer_test.go`](../internal/visualizer/visualizer_test.go)**:
   - Assert that generated dashboard HTML contains `<details id="comparison-guide"` without an `open` attribute on that element (collapsed by default).
   - Assert presence of the lifecycle primer, all 4 subsystem group headings, explanations for all 10 columns, all 5 verdict badge descriptions, and `data-tip=` attributes on all 10 `#comparison-table` `<th>` headers.
3. **Verify & Regenerate**:
   - Run `go test -v -race ./...` in `mem_eviction_lab/`.
   - Rebuild `bin/visualizer` via `make build` and regenerate `comparison_dashboard.html` against `results/otlp-*` so the updated dashboard is immediately ready to inspect.
